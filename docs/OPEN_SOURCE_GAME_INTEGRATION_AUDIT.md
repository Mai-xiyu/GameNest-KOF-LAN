# 开源游戏接入复选与麻将候选审计

更新于 2026-09-26。本文只记录已打开源码后能由一手证据支持的结论。README 声称、源码存在、本地可运行和真人验收是四个不同等级。本轮未在 Docker 中运行候选，也未进行真人联机。

## 当前结论

1. GameNest 内置麻将、斗地主及其他未复核规则游戏继续保持“内置原型”，正式大厅不展示，服务端默认拒绝创建；西洋跳棋是唯一按本轮证据单独放行的固定上游模块预览，不代表其余内置游戏恢复发布。
2. 停止继续扩写本地麻将和斗地主规则。后续只做安全修复、数据迁移和适配层，不用新的自写规则补齐上游缺口。
3. `touourin/game-hall` 的斗地主是目前证据最强的开源斗地主候选；它不能作为“另一套大厅”直接嵌入 GameNest，必须在“切换主大厅”和“抽取上游游戏模块”之间二选一。
4. `yemaster/mamahjong@c903603cfefc5786126173b33468e7df001280de` 已作为独立开源上游接入预览：保留其 Rust/Axum 服务端、React 客户端、规则、房间、同步、聊天和逐玩家私牌投影，仅通过构建期与代理适配平台身份、同源路径和返回大厅。单浏览器已完成启动、进入大厅、选择四川麻将和创建好友房的预检；平台结算、真人多设备、断公网和 Docker/Linux 验收仍未完成，因此不得标为正式游戏。
5. 默认大厅只展示带固定上游提交的接入预览或明确候选；未复核的 GameNest 内置原型及其榜单没有浏览器入口。没有完成真人联机和离线 LAN 验收的玩法不得标成正式游戏，西洋跳棋因此仍为 `preview`。

## 拳皇 Wing 1.85 用户资源接入记录

拳皇 Wing 不属于已确认可再分发的开源游戏。当前只复用用户本地提供的 `kof_wing_1.85_html5` 资源包，游戏 SWF 固定 SHA-256 为 `6c45fdc725d4910da5335ed74b66b6540b4bbdeffb74602b7b6c49185bc6e297`；Ruffle 固定为 `@ruffle-rs/ruffle@0.6.0`。生成资源在 `output/kof-wing`，不提交 Git，也不应在未确认游戏权利的情况下推送到公开仓库或镜像仓库。

接入采用房主单权威 SWF + 局域网 WebRTC 画面 + 平台 WebSocket 访客输入，不复制两个 Flash 实例做伪同步，也不重写角色、素材、战斗和规则。跨设备首轮暴露的 offer 时序与 ICE 地址问题已改为访客就绪协商，并增加同主机 UDP 本地 STUN；Ruffle 强制 Canvas 兼容渲染并提供重载按钮。两个独立浏览器会话已进入实际 PVP 战斗并验证访客移动和按键注入；两台真实设备、真人整局、Docker、实体手机和阻断公网仍未验收，因此只在资源存在时运行时升级为 `preview`。

完整记录见 [KOF_WING_INTEGRATION.md](KOF_WING_INTEGRATION.md)。

### 未采用的独立候选

- `kbennett2000/lan-games@47da57fde05a28c23fedaecc1032300bfd25b967`（MIT）具有服务端 Checkers、Socket.IO 房间、SQLite、聊天、重连和观战。固定提交的 Checkers／通用管理单测共 69 项通过；但其锁定生产依赖在 2026-09-26 的 `npm audit --omit=dev` 中有 9 项告警（3 high、6 moderate），Windows Node 26 下跳过安装脚本后 `better-sqlite3` 无可加载绑定。自动修复仍剩 `uuid` 告警，因此本轮不把整套第二大厅和账号系统打进镜像。
- `logvisionn/checkers-ai-web@732da7ab4bc8ff4acbdd716252bbc48d01ffa68a`（MIT）的多人 WebSocket 端点只把浏览器消息转发给同房连接；服务端不校验座位、回合、走法、棋盘或胜负，不能作为权威真人联机实现。

## `MaMahjong` 适配边界与当前状态

- 固定上游提交并通过构建期补丁适配 `/g/mamahjong/` 静态资源、HTTP 和 WebSocket 路径；不把 React 页面或 Rust 规则重写成 GameNest 原生游戏。
- 增加只在回环接口接受的平台启动授权兑换，让上游会话绑定 GameNest 稳定 `player_id` 和昵称；浏览器不能提交或覆盖真实身份。
- 将上游大厅默认裁剪为“局域网房间”的创建／加入入口，隐藏段位、角色、牌谱与上游账号退出按钮；不改动牌局规则、房间协议、同步或服务端投影。
- 评估两条持久化路径：在同一镜像监督 PostgreSQL，或为上游身份仓储增加 SQLite 实现。前者镜像和运维成本高，后者改动代码多；不能默默退化为内存身份。
- 对 Windows 候选预览定点跳过不受支持的目录 `sync_all`，但 linux/amd64 正式构建仍保留并验证目录落盘语义。
- 从服务端已生成的终局牌谱接入平台结果，按玩法、规则快照、三／四人和可信等级分组；不接受客户端自报输赢。
- 保留上游按观察者生成状态／事件的实现，并补四会话抓包、观战／牌谱权限、重连旧会话失效、返回大厅再进入和跨身份代操作反例。

已落地的是前两项中的路径、平台身份、回环代理、返回大厅和 Windows 归档兼容；`Dockerfile` 已把固定上游、前端产物与 Rust 服务器写入单镜像构建链，但本机无 Docker，尚未实际构建。结算适配和四真人完整牌局仍是未完成项。

## `Blood-On-Mahjong` 必需改造（后备方案）

- 由大厅服务端签发一次性启动授权，游戏服务端换取玩家 ID；客户端不得提交 `userId` 作为身份依据。
- WebSocket 连接绑定已验证身份和座位，动作处理不接受客户端自报 `playerId`。
- 服务端对每个收件人生成独立视图；私牌、牌墙和其他玩家可用动作不得出现在公共广播或仅凭查询参数返回的 HTTP 响应中。
- 删除客户端可发的 `game:state-update`；客户端只能提交规则动作。
- 房间以稳定玩家 ID 而不是 Socket ID 保留座位，明确断线宽限、旧连接失效和房主重连行为。
- 把 MongoDB/Redis/Google OAuth 改为可在单镜像内离线运行的存储和身份适配，或明确接受打包多进程数据库的运维代价。
- 增加四会话状态泄漏反例、跨会话代操作、断线重连、观战、完整一局和幂等结算测试。

这些是对上游网络与身份边界的重构，但仍可保留其麻将规则、计分、牌组、前端和部分房间流程。只有在改造范围被显式批准后才能进入实施，不得把它暗中等同于“小适配”。

## 建议接入顺序

1. `MaMahjong` 的最小构建期适配、Windows 归档兼容、平台启动授权、稳定身份、同源路由和返回大厅已落地；继续补四个隔离会话的建房、私牌、出牌、重连和终局牌谱验证。
2. 从上游服务端牌谱接入平台结果，完成三／四人分模式记录；不接受客户端自报成绩。
3. 在隔离环境启动固定提交的 `touourin/game-hall`，实测斗地主三会话建房、叫抢、出牌、重连、结算与私牌抓包；再决定切换主大厅还是抽取上游游戏模块。
4. 上游游戏通过真人、断公网、单镜像与规则验收后才启用。`Blood-On-Mahjong` 保留为后备，不再作为麻将首选。
